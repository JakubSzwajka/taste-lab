# AGENTS.md

taste-lab is a local loop for tuning UI taste. The operator compares component variants side by side and logs a pick plus a reason. You (the agent) read that log and write the next round as files. The app never calls an LLM.

## Core principle: 100% shadcn

The goal is a shadcn component library that is easy to restyle later. Every variant is built from shadcn only.

- Compose stock primitives from `@/components/ui/*`. Never hand-build a widget a primitive already covers.
- Style only with theme tokens (CSS variables) and semantic Tailwind classes: `bg-card`, `text-muted-foreground`, `border`, `bg-primary`, `rounded-md`.
- No raw colors. No hex, rgb, hsl or oklch literals. No palette classes (`bg-blue-500`, `text-white`). No arbitrary color values (`text-[#333]`, `bg-[red]`, `[color:red]`). No `style` prop in variants: per-variant tokens go in `round.json`.
- Looks differ through composition, layout, spacing, type scale and per-variant token overrides in `round.json`.
- Never hand-edit `src/components/ui/*`. It is generated by the shadcn CLI. Add a primitive with `pnpm dlx shadcn@latest add <name>` only when a variant needs it.
- The app chrome (`src/**` outside `ui/`) follows the same color rule.

`pnpm test` enforces the import allowlist and the no-raw-colors rule on every `variants/**/*.tsx`. It passes with zero rounds.

## Variant file API

A variant is a `.tsx` file in a round folder. It default-exports a React component with no required props.

Allowed imports, nothing else:

| Import              | Use                        |
| ------------------- | -------------------------- |
| `react`             | hooks, types               |
| `@/components/ui/*` | shadcn primitives          |
| `@/fixtures`        | sample data and formatters |
| `@/lib/utils`       | `cn()`                     |
| `lucide-react`      | icons                      |

Available primitives: `avatar`, `badge`, `button`, `card`, `checkbox`, `dropdown-menu`, `progress`, `separator`, `table`, `textarea`, `toggle`, `toggle-group`, `tooltip`.

Fixtures, from `@/fixtures`:

- `tasks: Task[]` for item and card rounds. Fields: `id`, `title`, `status` (`todo | in-progress | in-review | blocked | done`), `priority` (`low | medium | high | urgent`), `assignee {name, initials}`, `due` (ISO date), `tags`, `comments`, `description`.
- `rows: Row[]` for table rounds. Fields: `id`, `name`, `owner {name, initials}`, `status` (`active | paused | at-risk | done`), `progress` (0 to 100), `amount` (USD), `updated` (ISO date).
- Helpers `formatDate(iso)` and `formatCurrency(n)`. Types `Task`, `Row`, `Person`.
- `fixtures` and `fixtureKeys` map the `fixture` key in `round.json` to data. Add a fixture by adding a key in `src/fixtures/index.ts`.

All variants in a round must render the same fixture data. Render the whole fixture (a list of cards, a full table), not one item.

```tsx
import { Badge } from "@/components/ui/badge";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { tasks } from "@/fixtures";

export default function Dense() {
  return (
    <div className="grid gap-2">
      {tasks.map((t) => (
        <Card key={t.id} size="sm">
          <CardHeader>
            <CardTitle>{t.title}</CardTitle>
          </CardHeader>
          <CardContent>
            <Badge variant="secondary">{t.status}</Badge>
          </CardContent>
        </Card>
      ))}
    </div>
  );
}
```

## Round contract

```
variants/
  round-001/
    round.json
    a.tsx  b.tsx  c.tsx      # 2 to 4 variants
```

`round.json`:

```json
{
  "id": "round-001",
  "level": "component",
  "component": "card",
  "question": "Which task card feels right?",
  "fixture": "tasks",
  "basedOn": null,
  "preview": "columns",
  "variants": [
    {
      "id": "a",
      "file": "a.tsx",
      "label": "Dense outline",
      "changes": "1px border, 12px padding, meta inline",
      "tokens": { "--radius": "0.25rem" }
    }
  ]
}
```

- `id` equals the folder name. Rounds sort by id. Use `round-001`, `round-002`, ...
- `level` is `token`, `component` or `layout`.
- `fixture` is a key of `fixtures`.
- `basedOn` is `null` or `{ "round": "round-000", "pick": "b" }`.
- `preview` is optional: `"columns"` (default) or `"flip"`. It sets how the compare screen starts. `columns` shows the variants side by side. `flip` shows one variant at full page width with A/B/C tabs. Use `flip` for tables and layouts that need width. The operator can switch at any time, so this is only the starting view. Any other value is a round error.
- `variants` has 2 to 4 entries. Each `file` is a `.tsx` file in the same folder. `label` and `changes` show in the frame header.
- A bad `round.json` shows a readable error for that round in the app. Other rounds keep working.
- The app finds rounds with `import.meta.glob`. No code change per round.
- Current round is the first round with no log entry. The operator can open any round.

### Token overrides

`tokens` is optional per variant. Keys are shadcn variable names (`--radius`, `--primary`, `--card`, `--muted`, `--border`, ...). Values are any CSS value for that variable.

The app writes them as inline `style` custom properties on the variant frame element. The `.dark` class sits on `<html>`, so inline custom properties on a descendant always win over both `:root` and `.dark` values. A token override therefore holds in light and dark mode. Corollary: an override applies in both themes. If a color must differ per theme, use `light-dark(a, b)`. The frame sets `color-scheme` to the active theme so this works. Prefer `oklch(...)` values to match the theme; literals are allowed in `round.json` only, never in `.tsx`.

## Taste log contract

`taste/taste.jsonl` is append-only, one JSON object per line:

```json
{
  "ts": "2026-...Z",
  "round": "round-001",
  "component": "card",
  "level": "component",
  "shown": ["a", "b", "c"],
  "pick": "b",
  "tags": ["airy", "clean"],
  "reason": "less noise",
  "theme": "dark",
  "view": "flip"
}
```

- `view` is optional: `"columns"` or `"flip"`, the view in use when the operator answered. Lines written before it existed have no `view` and stay valid.
- `pick` is a variant id from `shown`, `"none"` or `"mix"`. For `mix`, `reason` is required and says which parts.
- Tags come from: airy, cramped, loud, quiet, dated, clean, playful, serious, too much, too little.
- Never edit or reorder existing lines. Only the app middleware appends.

Endpoints, served by the Vite dev and preview servers (loopback only, Host must be 127.0.0.1, localhost or ::1):

- `POST /api/taste` validates the body and appends one line. `201 {entry}` on success, `400 {error}` on bad input.
- `GET /api/taste` returns `{ entries, skipped }`. `skipped` counts unreadable lines.

## The loop

1. Read `taste/taste.jsonl` and `taste/DESIGN.md`. Look at the winning variant files of recent rounds.
2. Write the next round in `variants/round-NNN/`. Set `basedOn` to the pick you build on. Change one thing per round. Make variants differ in clear directions.
3. Run `pnpm check` and `pnpm test`. Fix anything flagged.
4. Tell the operator to refresh the app and answer.
5. Every ~5 rounds, distill the log into `taste/DESIGN.md`: Do, Don't, Tokens, Open questions. Cite round ids.
6. Read tags and reasons. A "none" means all options missed. Change direction, not detail.

## Promoting a winner (later step, documented only)

Not automated in v1. When a direction is settled:

1. Copy the winning variant to `src/components/lib/<Name>.tsx` as a named component.
2. Give it `cva` variants for the axes that differed between rounds, and a `className` passthrough merged with `cn()`.
3. Move the winning `tokens` into the theme in `src/index.css` (`:root` and `.dark`).
4. Keep it built from `@/components/ui/*` only. Record the decision in `taste/DESIGN.md`.

## Known limits

- Overlay content (dropdown menus, tooltips) portals to `<body>`, outside the variant frame. It does not get the variant's `tokens` and uses the global theme. Generated `ui/*` is not hand-edited, so this stays. In token rounds, judge the in-frame surfaces, not the overlays.
- `pnpm test` parses each variant with the Vite parser. A file that does not parse is a violation. The scan is static: it cannot see colors built at runtime from strings.
- The taste log API accepts `POST` only with `Content-Type: application/json` and an `Origin` (if sent) equal to the serving origin. `ts` is set by the server. Tags outside the list are rejected with 400.

## Commands

- `pnpm dev` starts Vite on 127.0.0.1.
- `pnpm check` runs `tsc --noEmit` and Biome.
- `pnpm test` runs Vitest.
- `pnpm build` runs the type check and a Vite build.
- `pnpm format` runs `biome check --write .`.
